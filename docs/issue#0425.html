Implementation Notes

Issue #425 — 全 driver 收敛 (hook wiring convergence, FR-16) — 2026-07-30

Design Decisions

Decision Two wiring paths kept, not one

Ambiguity: The AC says "RunConfig 组装处统一调用 InstallHooks", implying a single entry point.

Choice: Kept two shapes — one-shot drivers (headless, subagent_rpc) call InstallDriverHooks/InstallHooks all-in-one; multi-turn drivers (repl, tui, goal, btw) call BuildDispatcher once at session start (so SessionStart fires exactly once) and InstallSeams per turn.

Rationale: A multi-turn session must not re-fire SessionStart or rebuild the dispatcher every turn. InstallHooks internally delegates to InstallSeams, so both paths converge on the same seam-wiring code — the "统一" requirement is met at the shared helper, not a single call signature.

Decision Host interface gained Dispatcher() / HookDeps()

Ambiguity: Side-runs (/goal, /btw) build their own RunConfig but must reuse the session's already-resolved dispatcher and deps.

Choice: Added two accessors to cli.Host, implemented only by replDeps. Side-run packages read them via the existing cli.Host contract.

Rationale: Avoids an import cycle (cli/run does not import cli) and avoids re-resolving hooks per side-run, keeping trust/session-id consistent with the parent session.

Decision Trust gate for non-interactive drivers via run.Trusted(cwd)

Ambiguity: FR-14 requires project-layer hooks only when trusted, but headless/tui/subagent have no live trust.Manager.

Choice: Added run.Trusted(cwd) reading the shared trust store, fail-closed (missing/unreadable store ⇒ untrusted).

Rationale: A checked-out repo cannot run arbitrary project-layer hook commands until the user explicitly trusts the directory, uniformly across every driver.

Deviations

Deviation Observer notifier chained onto each driver's event seam, not RunConfig

Spec implied: A uniform install would suggest one field on RunConfig carries the SessionEnd/PreCompact observer.

Implemented: runtime.RunConfig has no OnEvent field — OnEvent lives on StreamHandler / HeadlessConfig. So the hook notifier is composed into each driver's own event handler (REPL/goal/btw/tui via chain helpers, headless via HeadlessConfig.OnEvent).

Why: Threading a new field through runtime would leak hook concepts into the hook-agnostic runtime layer; chaining at the driver keeps the seam where the driver already owns event delivery.

Deviation TUI bridge signature changed to thread an observer

Spec said: Wire hooks into the RunConfig assembly.

Implemented: The TUI bridge (newStreamHandler/pump/startRun) previously delivered no observer events at all; added an onEvent func(agentcore.AgentEvent) param so both the plugin notifier and the hook notifier reach the TUI.

Why: Without this the TUI would silently drop SessionEnd/PreCompact hooks (and plugin events), diverging from the other drivers — a correctness gap, not just wiring.

Tradeoffs

Tradeoff Regression test at the convergence-helper boundary

Alternatives: (a) full provider-backed run of each of the six drivers asserting a hook fires end-to-end; (b) pin the two distinct wiring paths at the shared helpers.

Chosen (b): TestHookConvergenceBothPaths drives the one-shot path (InstallDriverHooks) and the multi-turn path (BuildDispatcher+InstallSeams) with the same PreToolUse hook set and asserts the BeforeToolCall seam blocks in both; TestHookConvergenceNoHooksUnchanged pins FR-18.

Why it won: Every driver routes through exactly these two helper shapes, so the boundary test covers "same config fires in both modes" without standing up six fake providers — faster, deterministic, and pinned to the actual convergence point.
