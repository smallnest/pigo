Implementation Notes

Issue #541 — Responses 驱动 — 工具/函数调用 — 2026-08-02

Design Decisions

Decision Terminal tool calls parsed from response.completed; stream events only drive incremental partials

Ambiguity: A streamed tool call surfaces both as an output_item.done event (per finalized function_call) and inside the final response.completed envelope. The spec doesn't say which is authoritative for the terminal message.

Choice: mapResponse re-parses tool calls from resp.Output for the terminal StreamDoneEvent; the accumulated toolCalls slice from output_item.done only feeds interim StreamToolCallEvent partials (and a fallback when no completed event arrives).

Rationale: Reusing mapResponse keeps the streamed terminal message byte-identical to the non-streamed path, and both interim and terminal tool calls derive from one toolCallContent mapper so they can't diverge.

Decision Tool-result backfill keyed on the model's call_id

Ambiguity: The Responses API pairs a request and its result across turns; the spec doesn't prescribe the pairing key.

Choice: A prior AssistantMessage's ToolCallContent replays as a function_call input item (id/name/arguments), and the following ToolResultMessage replays as a function_call_output item — both keyed by the same call_id.

Rationale: call_id is the API's own correlation handle, so replaying it verbatim lets the model pair request and result without pigo inventing an id scheme.

Decision Message replay dispatched by type via appendInputItems

Ambiguity: #539/#540 replayed every message as plain text; tool turns need structured items instead.

Choice: A type switch replays ToolResultMessage → function_call_output, AssistantMessage → text + function_call items, and everything else → a role-tagged text message (the prior behavior).

Rationale: Localizes the tool wire format in one function and leaves the text path unchanged for non-tool turns.

Deviations

None — implementation followed the issue spec (tools sent as Responses functions, tool calls parsed to pigo types, results backfilled, multi-turn round-trip covered by stub tests).

Tradeoffs

Tradeoff strict:false for function tools

Alternatives: Enable Responses strict-function mode for schema-validated arguments.

Chosen: Pass strict=false to ToolParamOfFunction.

Why: pigo tool JSON Schemas aren't authored against the strict contract (which demands additionalProperties:false, all fields required, etc.); enabling strict would reject valid pigo tools at the wire.

Tradeoff Malformed/empty tool schema falls back to an empty object schema

Alternatives: Error out, or drop the tool, when its schema is empty or not a JSON object.

Chosen: Fall back to {} so the tool still reaches the wire with a valid (if permissive) parameter schema.

Why: A tool with a degenerate schema is still callable; silently dropping it would make the model unaware of a capability the user registered.

Open Questions

Question Function-call argument delta events are ignored

The stream switch handles output_item.done (finalized call) but not ResponseFunctionCallArgumentsDeltaEvent. Incremental argument text isn't shown token-by-token — the pending call surfaces only once it finalizes. Acceptable for this milestone; confirm whether live argument streaming is wanted later.

Question Tool-result content is text-only

function_call_output is built from contentText, so non-text tool results (images/structured blocks) are flattened to their text portion. Rich tool-result content depends on the image work in #542.
