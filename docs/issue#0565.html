Design Decisions

Decision Delivery rides the existing GetFollowUpMessages seam, not a timer goroutine

Ambiguity: The spec said reminders are delivered "when the agent is fully idle" but not by which mechanism.

Choice: Schedule.FollowUpMessages is wired as RunConfig.GetFollowUpMessages; the outer loop already consults that seam exactly when a run is about to settle, which is pigo's definition of "idle".

Rationale: Zero new goroutine lifecycle, deterministic delivery points, and the delivered reminder enters AgentContext.Messages as a real user turn — persisted and compacted like any other turn, which a background-timer injection could not guarantee.

Decision Store and tools live in agenttool, surfaced via ScheduleFromTools

Ambiguity: The spec did not say which package owns the scheduler.

Choice: The store and three tools live in internal/agenttool (no import cycle with runtime); SetupEnv puts the store on Env.Schedule and front-ends extract it from the tool set via agenttool.ScheduleFromTools.

Rationale: Mirrors the established MemoryStoreFromTools / BashJobStoreFromTools extraction pattern, so REPL/TUI/headless/SDK wiring stays symmetric and the tool-policy filter automatically disables the scheduler when it removes schedule_create.

Decision Strict time grammar: at XOR {date,time,time_zone} XOR every_seconds

Ambiguity: The spec listed the accepted shapes but not how mixed or partial input should behave.

Choice: Exactly one shape must be present; a partial date/time/time_zone triple is an error; "Local" is rejected as a zone; DST spring-forward gaps are rejected via a wall-clock round-trip check; fall-back overlaps resolve to the first instant; every stored target is normalized to UTC.

Rationale: Matches dsh's documented strictness; Go's time.Date normalization silently shifts gap times, so the round-trip check is the only reliable gap detector.

Deviations

Deviation dsh's after_seconds form omitted

Spec: dsh's overlay accepts after_seconds (relative delay), an absolute at, or every_seconds.

Implemented: Two shapes — absolute (at / date+time+time_zone) and fixed-rate (every_seconds) — per the issue text.

Why: after_seconds is sugar for an absolute instant computed client-side; the model can pass at directly. Trivial to add later without breaking the tool contract.

Deviation "REPL 端到端演示" acceptance satisfied by a loop-level integration test

Spec: Acceptance asked for a REPL end-to-end demo of create → due → follow-up injection.

Implemented: TestLoopDeliversDueScheduleReminder drives the real loop + real executor + real delivery seam against a scripted provider, asserting the reminder lands in the third request's context. REPL/TUI/headless/SDK are fully wired (deps.schedule → cfg.GetFollowUpMessages).

Why: An interactive REPL demo needs a live LLM key and human observation; the loop seam is the component that actually implements delivery, so the automated proof lives there.

Tradeoffs

Tradeoff Embedded time/tzdata (~450KB) vs Windows correctness

Alternatives: (a) embed the IANA database; (b) rely on the system zone database; (c) document IANA zones as unsupported on Windows.

Chosen: (a). goreleaser ships windows targets where the system tz database does not exist, so (b) breaks schedule_create at runtime and (c) ships a silent platform gap.

Why: ~450KB binary growth is cheap for correct DST rules on every release target (review finding, fixed).

Tradeoff Extended NewConfig signature vs an options struct

Alternatives: add an eighth parameter, or refactor NewConfig to take an options object.

Chosen: parameter, with the scheduler optional (nil = seam unwired).

Why: Two call sites; an options-struct refactor would touch every driver for one field. Revisit if the config keeps growing.

Open Questions

Question Should repeating reminders cap total deliveries?

dsh does not cap them within a session; pigo currently re-arms forever while the session lives. A max_fires argument or an idle-bounce guard (skip delivery when the previous turn was also this reminder) could be added if long sessions see noise.

Question Should /status or the system prompt surface active reminders?

dsh shows a reminder catalog in the Web UI header. pigo currently exposes reminders only through schedule_list. A /status line would be user-facing; a prompt hint would be model-facing. Both are additive follow-ups.
