Implementation Notes

Issue #332 — 模板参数展开引擎 — 2026-07-27

Design Decisions

Decision Single left-to-right pass instead of “expand ${...} then bare $” two-phase

Ambiguity: The AC says “先处理 ${...} 形式，再处理裸 $N/$@/$ARGUMENTS” (process braced before bare), which suggests two phases.

Choice: One left-to-right scan that consumes a ${...} as a single unit and a bare $N/$@/$ARGUMENTS as encountered.

Rationale: A single pass naturally satisfies the ordering invariant — because ${...} is consumed whole, a bare $1 can never match inside ${1:-...}, and a default literal containing $ is appended verbatim (never re-scanned). Two phases would require shadowing/protecting substituted text to avoid re-expansion — more error-prone.

Decision $@ expands to ALL args (not “the rest after positionals”)

Ambiguity: The pi docs example named $1 with features: $@ reads as if $@ is “the remaining args” (features shouldn't include the name), but the AC says “全部参数” and bash semantics are $@ = all positional params.

Choice: $@ = all args joined; “the rest” is expressed with the slice form ${@:2}.

Rationale: Matches the AC verbatim and bash convention. The slice form is the correct, explicit tool for “remaining args”.

Decision No-placeholder append uses Join(args, " ") (tokenized), not the raw arg string

Ambiguity: The old ParseUserCommand appended the raw args string (preserving quotes). ExpandTemplate receives tokenized []string.

Choice: Append strings.Join(args, " ") after a blank line.

Rationale: The existing TestParseUserCommand (e.g. Expand("buy milk") -> "Take a note\n\nbuy milk") passes because Join(["buy","milk"], " ") == the raw string for unquoted input. Quotes were grouping syntax, so dropping them in the append is the more correct behavior.

Deviations

None — implementation follows US-002 as written. All six placeholder forms, the ordering invariant, the no-placeholder append, and the test matrix (including the spec's component/bullets examples) match the acceptance criteria.

Tradeoffs

Tradeoff Hand-written scanner vs regex-based substitution

Alternatives: A chain of regexp.ReplaceAllFunc calls, one per form.

Pros/cons: Regex is compact but needs careful negative lookbehind to avoid $1 matching inside ${1:-...}, and still risks re-expanding substituted text. A scanner gives explicit control over the no-re-expansion guarantee.

Why it won: The ordering/no-re-expand invariant is the acceptance-critical part; an explicit scanner makes it obvious and testable.

Tradeoff Unknown ${name} expands to "" (shell-like unset var)

Alternatives: Emit the literal ${name} for unknown names.

Pros/cons: Empty matches bash semantics (unset variable); literal passthrough would preserve a typo for the user to notice. The AC has no case for unknown names.

Why it won: Shell consistency; ${@:N} on an invalid index already returns "", so unknown -> empty is consistent.

Open Questions

Question $@ = all-args vs “rest”: confirm against pi's runtime

Assumption: $@ = all args (per AC “全部参数”). The pi docs example is ambiguous on this point.

Verify: If a pi parity test or the reference implementation shows $@ means “remaining after positionals”, revisit. For now ${@:2} is the documented way to get “rest”.

Question No-placeholder append drops quotes from tokenized args

Assumption: For a no-placeholder template, appending Join(args, " ") (no quotes) is acceptable and matches the tested behavior.

Verify: #333's ParseUserCommand fallback (split failure -> treat raw arg string as $ARGUMENTS) must preserve the raw string on that path so a genuinely unparseable invocation isn't silently de-quoted.

Question Unknown ${name} silently becomes empty

Assumption: A typo like ${nmae} expands to "" with no warning.

Verify: Acceptable for now; consider a debug-mode warning if users report confusion. Not worth a hard error since ${...} is also used for valid slice/default forms.
