Implementation Notes

Issue #418 — hooks: ConfigLayer.Hooks 分层配置与合并 — 2026-07-30

Design Decisions

Decision Hooks append-merge, not field-level override

Ambiguity: Every other ConfigLayer field uses field-level replacement (higher layer wins). The spec (§3.2, FR-2) says hooks must accumulate across layers instead.

Choice: In ResolveConfig, hooks are appended per event type in ascending layer order (cfg.Hooks[evt] = append(cfg.Hooks[evt], matchers...)), while scalars keep override semantics.

Rationale: A global hook (e.g. an audit log on every tool call) must still fire even when a project adds its own hooks. Override would silently drop the global hook.

Decision Leave cfg.Hooks nil when no hooks defined

Ambiguity: FR-18 requires the no-hooks path to cost nothing, but does not specify the empty representation.

Choice: Only allocate the map on first real matcher; a layer carrying an event key with an empty matcher slice does not allocate either.

Rationale: Downstream dispatch can do a single nil check to skip all hook machinery, matching NewDispatcher's nil-set shortcut from #417.

Deviations

Deviation run.go hook loading deferred to #419

Spec said: #418 mentions run.go should load global + project hook layers (project only if trusted).

Implemented instead: Only the config plumbing (ConfigLayer.Hooks, Config.Hooks, merge in ResolveConfig) plus tests. The existing ResolveThinkingLevel helper already threads all layers through ResolveConfig, so hooks are merged today; the actual dispatcher wiring and trust-gated project loading belong to #419's InstallHooks helper.

Why: The issue itself flags "final wiring may defer to #419". Adding a half-wired dispatcher now would be dead code until #419's skeleton lands.

Tradeoffs

Tradeoff Shared slice backing on appended matchers

Alternatives: (a) append matcher values directly (shared inner Hooks slice headers), or (b) deep-copy each matcher.

Chosen (a): Resolved config is treated as read-only after ResolveConfig, so sharing the backing array is safe and avoids per-resolve allocation.

Con: A future caller that mutates cfg.Hooks in place could alias a layer's slice — acceptable given the read-only invariant, worth revisiting if config becomes mutable.

Open Questions

Question Should hook config be validated at resolve time?

Assumption: HookConfig.Validate() exists (#417) but is currently invoked lazily at match/dispatch time, not during ResolveConfig.

Verify: Whether a malformed hook (bad type / empty command) in a config file should fail the whole run early, or continue to be skipped-with-warning at dispatch. Current behavior: skipped at dispatch (consistent with fail-open isolation).
