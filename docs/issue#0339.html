Issue #339 — CLI flags --prompt-template / --no-prompt-templates — 2026-07-27

Design Decisions

Decision Reused one tier-agnostic loader (loadPromptPaths) for both settings and CLI tiers

Ambiguity: #338 added loadSettingsPrompts for settings; should #339 add a parallel loadCLIPrompts?

Choice: Renamed loadSettingsPrompts -> loadPromptPaths (tier-agnostic: loads file/dir, warns on missing) and used it for both, with the caller doing AddSettings vs AddCLI.

Rationale: The loading logic is identical across tiers; only the registration tier differs. One function avoids duplication.

Decision --no-prompt-templates gates only prompt-template loading; skills and built-ins unaffected

Ambiguity: Should the disable flag also suppress skills (since skills surface as /skill-name commands)?

Choice: srcs.disable gates the global/settings/CLI prompt-template loading only; skill registration (AddSkill) and built-ins run unconditionally.

Rationale: The AC says “built-in 斜杠命令不受影响” and “--no-prompt-templates 与 --no-skills 互相独立”. Skills have their own --no-skills flag; conflating them would violate the independence requirement.

Decision Carried the disable flag on promptTemplateSources.disable

Ambiguity: Where to plumb --no-prompt-templates?

Choice: Added disable bool to the promptTemplateSources struct introduced in #338 (no new signature change).

Rationale: The struct was designed to carry all prompt-template discovery state; the disable flag is part of that state.

Deviations

Deviation Renamed loadSettingsPrompts (from #338) to loadPromptPaths

Spec said: #338 named the loader loadSettingsPrompts (settings-only intent).

Implemented instead: loadPromptPaths (tier-agnostic), reused for CLI. Updated the #338 test call.

Why: The function was already tier-agnostic in behavior; #339 just makes the name honest and reuses it. A rename is lower-cost than a parallel function.

Tradeoffs

Tradeoff Gate at load time (skip disk) vs load-then-filter

Alternatives: Always load all sources, then drop prompt-template commands if disable is set.

Pros/cons: Load-time gating avoids touching disk (faster, no spurious warnings for paths that won’t be used). Load-then-filter is simpler control flow but reads files pointlessly.

Why it won: Skipping disk is cleaner and avoids warning about --prompt-template paths when the user explicitly disabled templates.

Tradeoff disable on the sources struct vs a separate buildSlashRegistry param

Alternatives: A 5th boolean param.

Pros/cons: The struct already exists; reusing it keeps the signature stable. A separate param would be more visible but means another churn.

Why it won: Stability; disable is conceptually part of the prompt-template sources.
