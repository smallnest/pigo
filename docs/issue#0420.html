Implementation Notes

Issue #420 — hooks: PreToolUse + PostToolUse 接线 — 2026-07-30

Design Decisions

Decision PreToolUse chains after the trust gate, never replaces it

Ambiguity: The BeforeToolCall seam is already occupied by trust.BeforeToolCall. How to add a hook without losing the trust gate?

Choice: InstallHooks wraps the existing seam via chainBeforeToolCall(existingTrust, preToolCallHook). Trust runs first; a trust block short-circuits before the user hook runs.

Rationale: Keeps the trust gate authoritative (issue's key constraint) while layering user hooks on top. Matches the block-short-circuit combinator semantics defined in #419.

Decision updatedInput is re-validated against the tool schema

Ambiguity: Spec says a PreToolUse hook may rewrite tool args; it does not say whether the rewrite is trusted.

Choice: The executor replaces args with UpdatedInput and re-runs Registry.Validate; a schema-invalid rewrite becomes a validation error result.

Rationale: A hook must not be able to smuggle malformed arguments past the tool's own schema contract.

Decision PostToolUse feedback is appended, block is advisory

Ambiguity: What does a PostToolUse block mean for an already-executed tool?

Choice: Post cannot undo execution. reason + additionalContext are joined and appended as a new text block onto a clone of the result content via AfterToolCallResult.Content.

Rationale: The tool already ran and had side effects; the only honest action is to surface the hook's feedback to the model, not pretend the call didn't happen.

Deviations

Deviation Added an optional field to BeforeToolCallDecision

Spec said: Reuse BeforeToolCallDecision{Block, Content} for PreToolUse.

Implemented instead: Added an additive optional UpdatedInput json.RawMessage field, since the original struct could only block, not rewrite args.

Why: The updatedInput acceptance criterion cannot be expressed by the block-only struct. SPEC §4.5 sanctions additive optional fields as non-breaking.

Tradeoffs

Tradeoff tool_response payload = marshaled result content, not a typed shape

Alternatives: (a) marshal the whole AgentToolResult, (b) marshal only result.Content, (c) define a dedicated wire type.

Chosen (b): Passes the content the model would see, which is what a Post hook wants to inspect. Marshal failure degrades to an empty (omitted) field.

Con: Post hooks don't see IsError / Terminate flags. Acceptable for v1 observation/feedback; revisit if a consumer needs the full result.

Open Questions

Question Should InstallHooks be idempotent across repeated calls?

Assumption: InstallHooks is called once per run. Calling it twice would double-wrap the seams (hooks fire twice).
