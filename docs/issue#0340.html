Issue #340 — REPL Tab 补全展示 argument-hint + description — 2026-07-27

Design Decisions

Decision Label format: name <argument-hint> - description, segments omitted when absent

Ambiguity: How to combine name, hint, and description?

Choice: name + (" " + hint if hint) + (" - " + description if description). The hint is shown verbatim — frontmatter supplies its own <angle>/[square] brackets, so no extra wrapping.

Rationale: Matches pi’s autocomplete rendering. Omitting empty segments keeps bare commands readable as just name.

Decision Slash commands render as -> {label} inline (existing arrow convention); Tab still inserts /name

Ambiguity: Where to show the label given pigo’s inline-cycling autocomplete (no columnar dropdown)?

Choice: In render(), slash-command candidates take a dedicated branch that prints -> {label} dimly (reusing the existing -> suggestion form). Non-slash candidates (history, models) keep the prior suffix/arrow behavior. The inserted candidate is still /name.

Rationale: Reuses the existing single-line render; the label is a display annotation, not the inserted text, so Tab completion keeps inserting the bare command name.

Deviations

Deviation “列按现有补全列宽对齐” (columnar alignment) not implemented

Spec said: Render with column alignment, referencing “现有 /model 目录补全的排版”.

Implemented instead: Inline -> {label} rendering, because pigo’s autocomplete is inline-cycling (arrow keys cycle candidates, Tab accepts) — there is no columnar candidate list to align. The /model catalog uses the same inline-cycling mechanism, not a columnar layout.

Why: A columnar dropdown would be a separate UX feature (e.g. double-Tab to list all). The inline label delivers the hint+description information the AC asks for within the existing architecture.

Tradeoffs

Tradeoff Inline label vs a columnar candidate list

Alternatives: Add a multi-candidate columnar display (print all matching commands in aligned columns when several match).

Pros/cons: A columnar list shows more at once but is a larger UX change (row accounting in render, double-Tab trigger). The inline label is a minimal, low-risk change that surfaces the hint+description.

Why it won: Minimal risk; the AC’s testable core (the label rendering, 4 cases) is delivered and unit-tested. A columnar list can be added later as a follow-up.

Tradeoff Label replaces the inline name-suffix for slash commands

Alternatives: Show both the inline suffix (e.g. iew completing /rev->/review) and the label.

Pros/cons: Both would repeat the name (/review review <PR-URL> - …). The label alone is cleaner and more informative.

Why it won: The label already starts with the full name; the bare suffix adds no information the label doesn’t.
