Implementation Notes

Issue #331 — shell 风格参数分词器 — 2026-07-27

Design Decisions

Decision Reused github.com/kballard/go-shellquote rather than hand-rolling a tokenizer

Ambiguity: The spec named the library as an example ("如 github.com/kballard/go-shellquote"), not a mandate; other shell-quoting libs exist.

Choice: Added go-shellquote as a direct dependency and wrapped shellquote.Split in runtime.SplitArgs.

Rationale: The project's global rule is "复用而非自实现". go-shellquote is mature, single-purpose, has no transitive deps, and is pure parsing (no shell execution — no injection surface). Hand-rolling a quote tracker would be more code to test and maintain for no gain.

Decision Normalize nil to a non-nil empty slice

Ambiguity: The spec says empty input returns []. shellquote.Split("") returns a nil slice, which in Go is distinct from []string{} though both have len == 0.

Choice: SplitArgs converts a nil result into []string{}.

Rationale: Callers (the template expander in #332/#333) can rely on len(args) == 0 and range over the slice without a nil guard, and the acceptance criterion "空字符串输入 -> []" reads as a literal empty slice.

Deviations

None — implementation followed US-001 as written. The function signature SplitArgs(s string) ([]string, error), the quoting/stripping behavior, the empty/unclosed-quote handling, and the test matrix all match the acceptance criteria verbatim.

Tradeoffs

Tradeoff go-shellquote vs go-shellwords vs mvdan.cc/sh

Alternatives: github.com/mattn/go-shellwords (similar API, also popular, adds POSIX-escape helpers); mvdan.cc/sh/v3/shell.Fields (full shell parser, heaviest).

Pros/cons: shellquote is the most minimal (one file, zero transitive deps) and does exactly field-splitting with quote handling. shellwords brings options we don't need. mvdan/sh is overkill for splitting a single line.

Why it won: Minimal footprint, no transitive deps to audit, and the spec already pointed at it.

Tradeoff Wrapped SplitArgs instead of calling shellquote.Split directly from the expander

Alternatives: Have the template expander (#332) import shellquote directly and call Split.

Pros/cons: A direct call is one less function. A wrapper gives a stable pigo-internal API, centralizes the nil->empty normalization, and isolates the third-party dep to one file so the expander depends on runtime.SplitArgs, not shellquote.

Why it won: If we ever swap the quoting lib (or adjust edge-case behavior), only args.go changes. Worth the trivial indirection.

Open Questions

Question Backslash-escape semantics inside double quotes

Assumption: shellquote.Split interprets backslash escapes inside double quotes (e.g. "a\"b" -> a"b). The spec didn't mention escapes; I assumed shell-style escapes are desired since the feature is "shell 风格分词".

Verify: If a user wants a literal backslash inside a double-quoted prompt argument, they'd use single quotes. Confirm this matches pi's actual behavior in a parity pass; if pi treats backslashes literally, we may need a different splitter or pre-processing.

Question Empty-quoted-argument semantics ("" -> one empty arg)

Assumption: SplitArgs("") yields [] (no args), but SplitArgs("") (a literal empty double-quoted token) yields [""] (one empty arg), so $1 would be "". This is standard shell behavior.

Verify: The spec didn't specify this case. Confirm pi treats an explicitly-empty quoted arg as a present-but-empty positional (affecting ${1:-default}, which should NOT use the default since arg1 is present).
