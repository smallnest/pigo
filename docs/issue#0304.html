Implementation Notes

Issue #304 — 在 run/repl 装配层加载 skills 并注入 prompt — 2026-07-27

Design Decisions

Decision Load skills once in setupAgentEnv, share between prompt and slash commands

Ambiguity: Skills are needed in two places — the system prompt's <available_skills> block and the REPL's /skill-name registry. The spec didn't say where to load them.

Choice: Introduced loadSkills(noSkills) (bootstrap + LoadSkillsDir) called once in setupAgentEnv; the result is stored on agentEnv.skills, injected into the prompt, and threaded through interactiveOptions.skills into buildSlashRegistry.

Rationale: The skills directory is read a single time per launch. buildSlashRegistry shrinks to a pure registration loop over the pre-loaded set — no disk I/O, no bootstrap side effect buried in the REPL wiring.

Decision Reorder setupAgentEnv: build tools before the prompt

Ambiguity: BuildSystemPrompt now needs ReadToolAvailable, but the prompt was previously built before the tool set existed.

Choice: Moved tool + plugin assembly above BuildSystemPrompt, then computed hasReadTool(tools) and passed it plus the loaded skills into PromptConfig.

Rationale: The read-tool signal is derived from the actual resolved tool set (respecting --no-tools), not guessed. Mirrors pi's selectedTools.includes("read") check performed at assembly time.

Deviations

Deviation Built-in skill bootstrap now also runs in headless mode

Spec: Bootstrap was previously REPL-only (it lived inside buildSlashRegistry, reached only from runInteractive).

Implemented: Bootstrap moved into loadSkills, which setupAgentEnv calls on both the REPL and headless (-p) paths.

Why better: Model-invocable skills must be advertised in the prompt in every mode, including headless. Bootstrap stays silent unless PIGO_DEBUG is set, so no new output noise. Consistent with the feature goal that headless runs also see skills.

Tradeoffs

Tradeoff Removed the now-dead interactiveOptions.noSkills field

Alternatives: Keep the field for symmetry with the CLI flag, vs delete it since buildSlashRegistry no longer gates on it.

Chosen: Deleted it (surfaced during review — it was set but never read after the refactor).

Why it wins: --no-skills is already honored upstream in loadSkills(noSkills), so an empty skills slice fully expresses the disabled state. A set-but-unread field would mislead future readers into thinking the REPL re-checks the flag.

Open Questions

None — build, vet, and go test ./cmd/pigo/ ./internal/runtime/ all pass; behavior matches the PRD (skills loaded once, injected when read tool present, slash commands preserved).
