Design Decisions

Decision One source of truth, two frozen projections

Choice: The accumulator's TelemetryEvent maps through a pure function onto a canonical TelemetrySummary document (schema_version + snake_case), while the existing stream-json "telemetry" envelope keeps its historical camelCase names — both are pinned byte-for-byte by golden fixtures.

Rationale: Changing the stream-json field names would break existing consumers; freezing them converts an implicit contract into an explicit one at zero migration cost.

Decision Field-type assertions in addition to golden bytes

Choice: The conformance test decodes the document into a generic map and asserts each field's JSON type individually.

Rationale: A golden file alone would still pass if a Go type change altered one field's wire type in a way a byte-diff reviewer missed; explicit type pins catch semantic drift mechanically.

Deviations

Deviation Aligned with pi-telemetry's goal, not its span model

Spec: "对齐 pi-telemetry 的字段命名/语义，或提供 pi-schema 与 OTel/通用 JSON 双适配器".

Implemented: pi-telemetry is a span/attribute-based typed-schema system (spans, start/end attributes, conformance fixtures) — a different shape than pigo's run-summary. pigo adopts the contract properties (typed schema, versioned discriminant, golden conformance) on its run-summary model, and the "dual adapter" is realized as the two frozen projections (canonical document + stream-json envelope).

Why: A full span-model rework would rewrite the accumulator and every consumer for no current consumer demand; the chosen scope delivers the anti-drift guarantees the issue asked for.

Tradeoffs

Tradeoff Golden fixtures vs hand-written assertions

Chosen: goldens with an explicit -update-telemetry-goldens regeneration flag, stored under internal/runtime/testdata/telemetry/.

Why: Byte-level fixtures are the strongest anti-drift device for a versioned JSON contract; the update flag keeps legitimate version bumps (v2) a one-command regeneration plus review.
