Implementation Notes

Issue #338 — config.toml prompts 数组 — 2026-07-27

Design Decisions

Decision Pass prompt sources to buildSlashRegistry via a promptTemplateSources struct

Ambiguity: How to plumb config-provided prompt paths into the registry without churning the signature again for #339 (CLI flag + disable)?

Choice: A small struct promptTemplateSources{settings, cli} as a 4th param. #338 fills settings; #339 will fill cli and the disable flag without another signature change.

Rationale: One signature change covers both issues; the struct documents the discovery sources in one place.

Decision loadSettingsPrompts lives in cmd/pigo (stderr access); LoadPromptFile in runtime

Ambiguity: Where does the “file or dir, warn on missing” loader belong?

Choice: runtime.LoadPromptFile (single-file parse, pure) + cmd/pigo.loadSettingsPrompts (stat/warn/collect, has stderr).

Rationale: Keeps the runtime package free of stderr I/O; the warning is a user-facing concern owned by the CLI layer.

Decision Config prompts is always passed through (no CLI-flag override)

Ambiguity: The AC said “applyFileConfig 把 prompts 透传到运行时（CLI flag 未覆盖时）”, implying an override relationship.

Choice: Config prompts (settings tier) and #339’s --prompt-template (CLI tier) are additive, distinct tiers — both load, priority resolved by tier. So config is always passed when present.

Rationale: Tiered priority (global > settings > CLI) already handles same-name resolution; treating them as additive matches pi’s model. The “CLI flag 未覆盖时” phrasing is the generic applyFileConfig boilerplate, not a real override here.

Deviations

Deviation Changed 3 pre-existing config_file_test.go struct comparisons to reflect.DeepEqual

Spec said: (existing tests) cfg != (fileConfig{}) and cfg != want.

Implemented instead: !reflect.DeepEqual(cfg, fileConfig{}) / !reflect.DeepEqual(cfg, want).

Why: Adding the Prompts []string slice field makes fileConfig non-comparable (!= on a struct containing a slice is a compile error). This is a necessary side effect of the new field, not a behavior change.

Tradeoffs

Tradeoff promptTemplateSources struct vs separate params

Alternatives: Add settingsPrompts []string now and cliPrompts + disable in #339 as more params.

Pros/cons: Separate params mean two signature churns (and re-updating ~8 call sites each time). A struct is one churn.

Why it won: One signature change; #339 just fills more struct fields.

Tradeoff Warn to stderr on missing settings path vs silent skip

Alternatives: Silent skip (like missing global dirs).

Pros/cons: The AC explicitly wants a one-line warning for missing settings paths (they’re explicitly user-listed, unlike ambient global dirs). Silent skip would hide config typos.

Why it won: Match the AC; an explicit prompts = [...] entry that doesn’t resolve is almost certainly a typo the user wants to know about.
