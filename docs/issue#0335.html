Implementation Notes

Issue #335 — SlashRegistry 分层优先级解析 — 2026-07-27

Design Decisions

Decision Tier constants declared ascending (CLI=0 … Builtin=5) so “higher value wins”

Ambiguity: The spec defined the priority order (built-in > project > global > package > settings > CLI) but not how to encode it numerically.

Choice: TierCLI = iota … TierBuiltin (ascending), so a higher numeric value is higher priority and the resolver's existing.Tier > cmd.Tier reads naturally as “existing wins”.

Rationale: The first draft declared Builtin first (=0, lowest), which silently inverted the rule and failed every test. Ascending order makes the > comparison self-evident; the prose docs still list the human-readable order “built-in > … > CLI”.

Decision Changed Shadowed() from []string to []ShadowedEntry (Name+Tier+Source)

Ambiguity: The spec required Shadowed() to include the loser's tier; the old API returned only names.

Choice: New ShadowedEntry{Name Name, Tier, Source} with a String() -> "name (tier)"; updated all 3 in-repo callers (interactive.go + 2 tests).

Rationale: internal/runtime is internal-only, so no external API break. The richer entry lets /help (#341) and the startup warning name which source tier was shadowed.

Decision Skills/plugins map to TierGlobal; Source label preserved for display

Ambiguity: The spec said skills/plugins keep their source label but their tier is Global.

Choice: AddSkill/AddPlugin set Tier=TierGlobal and keep Source=SourceSkill/SourcePlugin.

Rationale: Priority-wise they compete equally with global user templates (last-write-wins within Global); the source tag still lets /status distinguish them.

Decision New prompt-template sources reuse SourceUser; Tier carries the distinction

Ambiguity: What Source label for project/settings/CLI/package templates?

Choice: AddProject/AddSettings/AddCLI/AddPackage all set Source=SourceUser and a distinct Tier.

Rationale: Avoids bloating the SlashCommandSource enum. /help (#341) renders source: <tier>, so Tier is the display key; Source remains the coarse builtin/user/skill/plugin tag.

Deviations

None — implementation followed US-009 as written. The Tier enum, central add() resolver, ShadowedEntry, the four new AddX methods, and the test matrix (project>global, global>settings, built-in>project, same-tier last-write-wins, full ladder) all match the acceptance criteria.

Tradeoffs

Tradeoff Central add() resolver vs per-method conflict checks

Alternatives: Keep the old per-method pattern (each AddX inlines its own built-in-wins check and shadowed append).

Pros/cons: Per-method duplicates the conflict rule across 4+ methods and is easy to get inconsistent. A central add() encodes the tier rule once.

Why it won: Single source of truth for priority; adding a new source tier is one new AddX wrapper, no conflict-logic duplication.

Tradeoff Tier as an int enum vs a struct with name+priority

Alternatives: A struct{Priority int; Name string} per tier.

Pros/cons: A struct is more self-documenting but heavier and not directly comparable with >. An int enum is lightweight, comparable, and idiomatic Go.

Why it won: The > comparison is the hot path in add(); an int keeps it trivial, and String() + the ascending-order comment document the meaning.

Tradeoff Same-tier override is silent (no Shadowed entry)

Alternatives: Record same-tier overrides in Shadowed too.

Pros/cons: Recording same-tier overrides would noise up Shadowed() with ordinary re-loads (e.g. re-reading ~/.pigo/prompts). The AC explicitly tests “同级后写覆盖” as a non-shadow case.

Why it won: Shadowed() stays a signal for real cross-tier conflicts only; same-tier re-load is normal and expected.

Question Tier zero-value is TierCLI (lowest)

Assumption: Every command reaches the registry via an AddX method that sets its Tier, so no command is ever installed with an unset (zero) Tier. A future caller that bypasses AddX and writes r.commands directly would silently get lowest priority.
