Implementation Notes

Issue #566 — feat: 在线拉取 provider 可用模型列表（Fetch available models） — 2026-09-12

Design Decisions

Decision One fetcher for both wire protocols

Ambiguity: The spec named OpenAI-compatible and Anthropic endpoints without saying how much they share.

Choice: provider.FetchRemoteModels(ctx, baseURL, protocol, apiKey) normalizes the protocol, picks the URL shape ({base}/models vs {base}/v1/models) and auth convention (Bearer vs x-api-key + anthropic-version), then parses one shared {"data":[{"id"}]} shape.

Rationale: Both protocols genuinely answer the same JSON shape, so a single parser avoids duplicated drift; the Responses protocol shares the Chat Completions path by design.

Decision Fetched ids pin the live provider on /model

Ambiguity: The spec said switching should accept fetched ids, but the default /model heuristic routes unknown ids to OpenRouter.

Choice: When the id is in live.FetchedModels, /model resolves with the live provider name explicit (ResolveProvider(..., live.ProviderName, ...)), keeping the id on the gateway that serves it; the result message notes "from fetched catalog".

Rationale: A gateway-specific id resolved through the heuristic chain could silently land on the wrong provider — the exact class of confusion #564 fixed for bare provider names.

Decision Credentials reach the slash closure via an explicit parameter

Ambiguity: RegisterLiveCommands / BuildSlashRegistry previously had no credential access.

Choice: Both take creds *provider.CredentialStore (nil = fetch disabled); the REPL passes its session store, the TUI builds one from the same options the run uses.

Rationale: Env-only key resolution would miss config.toml/--api-key overrides; dsh's fetch uses "the saved provider's stored key", which is the credential store's job.

Deviations

Deviation Cache is session-lifetime memory, not a disk cache

Spec: "可选缓存到本地（TTL）" was listed as optional.

Implemented: LiveConfig.FetchedModels/FetchedAt — refreshed on every /models fetch, never persisted.

Why: A disk cache adds staleness/invalidation questions (per provider? per base URL?) for little value: the fetch is one explicit command and takes milliseconds. Deferred until there's a real need.

Tradeoffs

Tradeoff Synchronous fetch in the slash action vs background refresh

Alternatives: block the REPL for up to 10s, or run the fetch async and update the catalog later.

Chosen: synchronous with a 10s client timeout + 15s action deadline; the fetch is user-initiated (/models fetch) and dsh's equivalent is likewise an explicit settings action.

Why: Async refresh would race the very /model switch the user is about to make; an explicit command with a visible result is easier to reason about.

Open Questions

Question Should fetched models also feed slash-command autocomplete?

The registry has ArgumentHint support; /model could complete against live.FetchedModels + presets. Skipped here because it touches the popup/filter UI shared by both front-ends — worth its own small change if wanted.

Question Should the fetch capability filter by the model's capabilities (vision, tools)?

The endpoint response sometimes carries metadata beyond id. Today we surface ids only, matching /model's contract. Capability-aware filtering would need per-provider metadata parsing.
