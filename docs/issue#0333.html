Issue #333 — 接入 ParseUserCommand：新引擎替换 $ARGUMENTS — 2026-07-27

Design Decisions

Decision On split failure, fall back to []string{args} (raw string as $ARGUMENTS)

Ambiguity: When SplitArgs errors (e.g. an unterminated quote), what should the expander receive?

Choice: Use a single-element token slice holding the raw arg string, so $ARGUMENTS expands to the raw input.

Rationale: Expand returns only a string (no error path), so the fallback must be silent. Treating the raw string as $ARGUMENTS keeps a bad invocation usable and matches the old strings.ReplaceAll behavior for $ARGUMENTS templates; no-placeholder templates still append the raw string.

Decision Removed the $ARGUMENTS-only fast path; all templates go through ExpandTemplate

Ambiguity: Keep a special-case strings.Contains(template, "$ARGUMENTS") branch for parity with the old code?

Choice: A single code path: SplitArgs then ExpandTemplate for every template.

Rationale: One path is easier to reason about; ExpandTemplate already handles $ARGUMENTS, the no-placeholder append, and the new positional/default/slice forms. The existing TestParseUserCommand regression test passes unchanged.

Deviations

None — implementation follows US-003 as written. Expand now does SplitArgs + ExpandTemplate with the documented raw-$ARGUMENTS fallback, and the regression + new (no-arg, quoted multi-arg, ${1:-7} default, split-failure) tests match the acceptance criteria.

Tradeoffs

Tradeoff Silent fallback vs surfacing an error

Alternatives: Change Expand to return an error, or log a warning from inside Expand.

Pros/cons: An error return would ripple through every Expand caller; a warning from Expand mixes I/O into a pure function. Silent fallback keeps Expand pure and the signature stable.

Why it won: The REPL layer (not Expand) is the right place for user-facing warnings; keeping the engine pure matches ExpandTemplate’s design.

Tradeoff Fallback sets $1 = raw string too (single-element tokens)

Alternatives: Special-case so only $ARGUMENTS gets the raw string while $1 is empty on split failure.

Pros/cons: Single-element tokens are simplest and coherent (one arg = the whole raw input). Special-casing $1 differently from $ARGUMENTS would be surprising.

Why it won: Coherence: on split failure the whole input is “one arg”, so $1 and $ARGUMENTS agreeing is the least surprising behavior.
