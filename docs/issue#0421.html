Implementation Notes

Issue #421 — hooks: UserPromptSubmit 接线 (注入 + 阻断) — 2026-07-30

Design Decisions

Decision additionalContext injected via a one-shot reminder, not a persisted message

Ambiguity: The spec requires the hook's additionalContext to reach the model on this turn but NOT enter persisted history. ReminderRegistry providers fire every turn.

Choice: Added OneShotReminderProvider (sync.Once) that emits its body on the first consultation, then stays silent. DispatchUserPromptSubmit registers one onto cfg.Reminders.

Rationale: Reminders are already ephemeral (injected into the per-turn request copy via TransformContext, never written back to AgentContext.Messages), so a one-shot provider gives exactly "this turn only, not persisted" — matching SPEC §11.3's explicit assumption.

Decision Block takes strict priority over injection

Ambiguity: What if a hook both blocks and returns additionalContext?

Choice: On dec.Block, return (true, reason) immediately and register no reminder.

Rationale: A blocked prompt is never submitted, so there is no turn to inject into. Injecting would leak orphaned context into the next unrelated prompt.

Decision Helper reports (block, reason); callers own the abort

Ambiguity: Block behavior differs per driver (REPL returns to input + shows reason; headless exits non-zero).

Choice: DispatchUserPromptSubmit only reports the decision; it does not abort. The two drivers map (block, reason) to their own control flow.

Rationale: Keeps the cli-layer helper driver-agnostic and testable in isolation, consistent with the #419/#420 seam-helper pattern.

Deviations

Deviation Per-driver call sites deferred to #425

Spec said: "REPL 与 headless 提示词入口均在提交前同步分发 UserPromptSubmit".

Implemented instead: #421 delivers the reusable mechanism (DispatchUserPromptSubmit + OneShotReminderProvider) and integration tests; the actual REPL/headless call-site wiring lands in #425 (全 driver 收敛), which converges every driver's InstallHooks + prompt gate at once.

Why: Same staging as #420 — wiring one driver in isolation would be undone by #425's convergence. The mechanism is complete and independently tested now.

Tradeoffs

Tradeoff One-shot state lives in the provider, not the registry

Alternatives: (a) fire-once flag inside the provider, (b) a registry that removes a provider after it fires.

Chosen (a): sync.Once in the provider keeps the registry a dumb append-only list and needs no mutation/removal API.

Con: A spent provider stays in the slice and is consulted (cheaply) every turn. Acceptable — a handful of prompt-submit reminders per session, each an O(1) no-op after firing.

Open Questions

Question Should the one-shot reminder survive a compaction boundary?

Assumption: If the prompt turn triggers compaction before the model consults reminders, the one-shot may fire against the post-compaction turn instead. In practice injection happens on the immediate next request, so this is not observed.

Verify: When #425 wires the real call sites, confirm the reminder is registered right before the loop's next request so the "next turn" is always the intended one.
