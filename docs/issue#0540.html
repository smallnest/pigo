Issue #540 — Responses 驱动 — 流式输出 — 2026-08-02

Design Decisions

Decision Terminal message built from response.completed, deltas only drive incremental partials

Ambiguity: A streamed run produces both incremental output_text.delta events and a final response.completed envelope. The spec (US-004) requires "final aggregation == non-streamed result" but doesn't say which source is authoritative.

Choice: Accumulate deltas into a running text partial for each StreamTextEvent, but map the terminal StreamDoneEvent from the completed envelope via the existing mapResponse (id, model, usage, text).

Rationale: The completed envelope is the same payload the non-streaming path (#539) maps, so reusing mapResponse guarantees byte-identical final messages across streaming and non-streaming — satisfying the acceptance criterion by construction rather than by matching two independent code paths.

Decision Fallback to accumulated delta text when no completed event arrives

Ambiguity: The spec doesn't cover a stream that ends cleanly (no transport error, no error event) but never sent response.completed.

Choice: If completed is nil at end-of-stream, build the terminal message from the accumulated delta text with StopReason=end_turn.

Rationale: Preserves whatever text the user already saw rather than dropping it or forcing an error; a truncated-but-clean stream is not a failure.

Decision Error events emitted via a background-context helper

Ambiguity: Context cancellation must "promptly stop the stream" (US-004), but emitting a terminal error on the pigo stream itself honors ctx — a cancelled ctx would drop the very error that reports the cancellation.

Choice: Added emitError which emits the terminal StreamErrorEvent using context.Background(), so the terminal error always lands regardless of the caller's ctx state.

Rationale: The consumer must always see a terminal event with StopReason=error; silently closing on a cancelled ctx would surface as ErrStreamIncomplete instead of a clear cancellation error.

Deviations

Deviation #539's non-streaming client.Responses.New call replaced by NewStreaming

Spec (prior milestone): #539 shipped a non-streaming skeleton that called Responses.New and derived a single text partial from the final message.

Implemented: pump now calls Responses.NewStreaming and consumes the SSE event union; the single-shot text partial is gone. The textContent helper that supported it was removed as dead code.

Why: #540 is explicitly the milestone that makes the driver stream; the non-streaming call was scaffolding. The wire body now sets stream:true (asserted in tests).

Tradeoffs

Tradeoff Test stubs emit SSE frames instead of a single JSON body

Alternatives: Keep #539's JSON-body stub for the endpoint/mapping test and only add SSE stubs for new streaming tests.

Chosen: Converted all driver tests to a shared sseResponse / deltaFrame / completedFrame helper set that mirrors the real text/event-stream wire format.

Why: The driver no longer has a non-streaming path, so a JSON-body stub would exercise nothing real — the ssestream decoder would silently yield zero events. SSE stubs test the actual code path.

Tradeoff Per-delta partial carries full accumulated text, not just the delta

Alternatives: Emit each StreamTextEvent carrying only the newest delta and let the consumer concatenate.

Chosen: Each partial carries the text accumulated so far (Hello → Hello, → Hello, world).

Why: Matches the existing partial semantics elsewhere in pigo (partials are cumulative snapshots), so the TUI renders a partial directly without tracking prior state. Verified by the incremental-delta test.

Open Questions

Question response.failed event carries no detail in the terminal error

A ResponseFailedEvent is mapped to a flat "response failed" message; its embedded Response may carry a richer error/status. If failed-run diagnostics matter downstream, consider surfacing the response's error detail. Deferred as out of scope for the text streaming milestone.

Question Reasoning/tool-call stream events are ignored this milestone

The event switch only handles text deltas, completed, failed, and error. Function-call argument deltas (#541) and reasoning summary deltas (#542) fall through silently — intentional for #540 but worth confirming those milestones layer onto this same switch rather than replacing pump.
