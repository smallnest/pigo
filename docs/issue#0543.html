Issue #543 — 将 resp_api 变体接入 ResolveProvider — 2026-08-02

Design Decisions

Decision resp_api with no --base-url errors (Open Question resolved: option B)

Ambiguity: The issue's Open Question asks whether --protocol openai/resp_api with no base-url should mirror anthropic (target the public api.openai.com/v1) or mirror openai (require an explicit --base-url).

Choice: Require --base-url; an empty base-url returns --protocol openai/resp_api requires --base-url, exactly like the plain openai Chat Completions path.

Rationale: The Responses driver (NewOpenAIResponsesProvider) carries no public default endpoint and is designed as a "point pigo at an endpoint that speaks this protocol" selector. Silently defaulting to a public OpenAI host would surprise self-hosted/gateway users and diverge from the sibling openai rule.

Decision Normalize the protocol once, switch on the canonical selector

Ambiguity: The pre-existing switch matched the raw surface value ("openai", "anthropic"), so "openai/chat" and "openai/resp_api" had no path and fell into the unknown-protocol error.

Choice: Call NormalizeProtocol(protocol) (from #538) at the top of the explicit-protocol block and switch on ProtocolOpenAI / ProtocolOpenAIResponses / ProtocolAnthropic / "".

Rationale: NormalizeProtocol already owns the surface-syntax parsing (trim, lower-case, alias collapse) and the unknown-value error, so reusing it collapses openai+openai/chat to one Chat Completions path and gives resp_api its own branch without duplicating parsing. The redundant default error was dropped because NormalizeProtocol now emits it earlier with a fuller message (lists all four accepted values).

Deviations

None — implementation followed the issue spec (resp_api routed to the Responses driver against base_url, openai/chat unchanged as Chat Completions, empty base-url handled by the resolved convention, --provider path untouched, resolve_test.go covers the new and unchanged paths).

Tradeoffs

Tradeoff Heuristic and --provider paths still receive the raw protocol string

Alternatives: Thread the canonical value through ResolveNamedProvider and the model-id heuristic calls too.

Chosen: Only the explicit-protocol switch consumes the canonical selector; ResolveNamedProvider still gets the raw protocol for its --provider/--protocol conflict check.

Why: Selecting the Responses driver via a --provider name is explicitly out of scope for this issue. A --provider foo --protocol openai/resp_api pair therefore raises the existing conflict error (raw "openai/resp_api" ≠ the spec's "openai" protocol), which is acceptable and avoids widening the registry's protocol vocabulary in this change.

Open Questions

Question No registry/provider-name route to the Responses driver

A built-in provider spec whose Protocol is openai always builds the Chat Completions driver via ResolveNamedProvider; there is no way to say "this named provider speaks the Responses API." If a first-party provider ever needs resp_api by name (not just by --protocol), the registry would need a third protocol value and a matching branch. Confirm that --protocol openai/resp_api is the only intended entry point for now.
