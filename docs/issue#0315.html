Issue #315 — 跨行光标移动 — 2026-07-27

Design Decisions

Decision 移动语义作为 mlBuffer 方法，editLoop 只做分派

Ambiguity: AC 规定了跨行移动与列裁剪行为，但未说明放在按键循环里还是缓冲区上。

Choice: 新增 left/right/up/down/home/end 六个 mlBuffer 方法承载全部移动语义（含跨行、列裁剪、边界 no-op），editLoop 只把按键映射到方法调用。

Rationale: 沿用 #313 的分层——每条移动语义可单测，按键分派保持薄。移动方法不触碰 lines，满足「光标移动不修改缓冲内容」。

Decision 单行 vs 多行决定 ↑/↓ 语义

Ambiguity: ↑/↓ 既要跨行移动光标，又要保留空行/单行的历史浏览，二者如何切换。

Choice: 以 !buf.single()（行数 > 1）为分界：多行时 ↑/↓ 移动光标；单行时走既有历史浏览 / 补全循环逻辑，零回退。

Rationale: 多行缓冲只在 Shift+Enter（#314）后出现，因此单行体验完全不变；AC 明确「单行且为空或光标在首行时仍历史浏览」，行数判据正好覆盖。

Deviations

None — 按 AC 实现：←/→ 行内移动且在行首/行尾跨相邻行、↑/↓ 多行移动并裁剪目标列、Home/End 与 Ctrl+A/Ctrl+E 行首行尾、移动不改内容、边界 no-op；构建/vet/测试全绿。

Tradeoffs

Tradeoff → 键：接受补全 vs 移动光标

Alternatives: (a) → 始终移动光标；(b) 有补全时 → 接受补全，否则移动光标。

Chosen: (b)。

Why it wins: → 接受补全是既有单行体验，直接改成移动会回退该行为。折中方案让「有可见补全时接受、无补全时移动光标」，两种需求都满足，且多行编辑场景通常无补全，跨行右移不受影响。

Tradeoff Ctrl+A/Ctrl+E 复用为行首/行尾

Alternatives: (a) 只支持 Home/End 转义序列；(b) 额外把 byte 1/5 映射为行首/行尾。

Chosen: (b)。

Why it wins: AC 允许「Home/End（或 Ctrl+A/Ctrl+E）」。byte 1/5 原先落入 default 会把控制字符插入缓冲（无用行为），改绑行首/行尾既满足 AC 又消除了这一隐性 bug，且是标准 readline 习惯。
