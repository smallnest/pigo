Implementation Notes

Issue #301 — skill frontmatter 支持 disable-model-invocation 与 name/description 校验 — 2026-07-27

Design Decisions

Decision Split validation into two standalone helpers

Ambiguity: The PRD required name and description validation but did not prescribe where the logic should live.

Choice: Added validateSkillName and validateSkillDescription as package-level functions rather than inlining the checks in ParseSkill.

Rationale: Standalone functions are directly unit-testable (see TestValidateSkillName/TestValidateSkillDescription) without constructing full skill files, and keep ParseSkill readable.

Decision Compile the name regexp once at package scope

Ambiguity: Where to build the ^[a-z0-9-]+$ matcher.

Choice: A package-level skillNamePattern = regexp.MustCompile(...).

Rationale: Avoids recompiling on every skill parsed; LoadSkillsDir can process 100+ skills.

Decision Validate after name defaulting, not before

Ambiguity: The order of file-base-name fallback vs validation.

Choice: Keep the existing fallback (name defaults to the file base name when frontmatter omits it), then validate. So a file My_Skill.md with no explicit name is validated as My_Skill and rejected.

Rationale: Matches PRD AC ("name 缺省时回退为父目录名或文件基名") while still guaranteeing every skill that reaches the prompt has a spec-compliant name.

Deviations

Deviation Skip-on-invalid-name vs pi's warn-but-keep

Spec said: pi's reference implementation (loadSkillFromFile in skills.ts) only drops a skill on a missing description; on a name-rule violation it emits a warning but keeps the skill.

Implemented instead: An invalid name makes ParseSkill return an error, so LoadSkillsDir skips that skill and accumulates the reason (non-fatal, other skills still load).

Why: The pigo PRD (US-002 AC) explicitly states validation failure follows pigo's existing "部分解析失败不致命" policy — skip and accumulate. A malformed name that reaches the <available_skills> block or the slash-command table could produce an unusable command name, so failing closed is safer for pigo. This is a conscious divergence from pi.

Tradeoffs

Tradeoff Byte-length vs rune-length for the 64-char limit

Alternatives: len(name) (bytes) vs utf8.RuneCountInString (runes).

Chosen: Byte length.

Why it wins: The name pattern already restricts input to ASCII [a-z0-9-], so bytes and runes are identical for any name that passes the pattern. The length check runs first, but a >64 multibyte string would still be rejected — either by length or by the ASCII-only pattern — so no valid skill is wrongly dropped and no invalid one slips through.

Tradeoff Reusing the existing "missing description" error string

Alternatives: Introduce a new sentinel error vs preserve the current message.

Chosen: validateSkillDescription returns the same "frontmatter missing required 'description'" text the old inline check used.

Why it wins: Keeps TestParseSkillRequiresDescription passing unchanged and avoids churning any caller that matches on the message.
