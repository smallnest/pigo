Implementation Notes

Issue #319 — 多行提交、历史记录与恢复 — 2026-07-27

Design Decisions

Decision 复用既有 String()/setString()/TrimSpace 路径，本 issue 以单测锁定行为

Ambiguity: AC 要求「多行作为一条历史、可复原为多行、完整传给 agent」，但这些能力大多已由前序 issue（#313 的 String() 以 \n 连接、setString() 按 \n 拆分）与 repl.go 现有提交路径铺就。

Choice: 审阅 repl.go 提交路径确认无需改生产代码：line := strings.TrimSpace(raw) 只去整体首尾空白、保留内部 \n；editor.remember(line) 把整块作为一条记录；prompt := line 把完整多行串传给 agent 一轮。补充 3 条单测把这条链路钉死。

Rationale: 行为已正确，加代码只会引入冗余；用测试锁定「多行进历史 / 历史复原为多行 / 提交串含 \n」防止后续回归，符合 issue 的 backend/验证性质。

Decision 历史复原后 ↑/↓ 优先做块内光标移动，而非继续翻历史

Ambiguity: AC 说复原多行后「可继续编辑」，但没说此时 ↑ 该翻更旧的历史还是移动光标。

Choice: 沿用 #315 的箭头分发：!buf.single() 时 ↑/↓ 走 buf.up()/down()（块内移动光标），仅单行/空行时才翻历史。

Rationale: AC 明确要「继续编辑」而非「继续浏览」；复原多行后光标移动是编辑的前提，优先编辑语义正确且与既有跨行移动一致。

Deviations

None — 按 AC 实现：多行块作为一条记录存入 e.history（保留内部换行）、空行 ↑ 复原为多行缓冲可继续编辑、remember 仅去整体首尾空白、提交串经 prompt := line 完整（含 \n）传给 agent。go build/vet 全包与 go test ./cmd/pigo/ 全绿。

Tradeoffs

Tradeoff 保留 TrimSpace vs 改为不 trim / 仅 trim 空白行

Alternatives: (a) 维持 strings.TrimSpace(raw)；(b) 完全不 trim，原样入历史与提交；(c) 逐行 trim。

Chosen: (a)。

Why it wins: TrimSpace 只削整体首尾空白、保留内部 \n，既满足 AC「不破坏内部换行」，又保留单行时误敲首尾空格自动清理的既有体验；(b) 会让误触的首尾空白进入 agent，(c) 会篡改用户有意的行内缩进。
