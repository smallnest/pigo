Implementation Notes

Issue #342 — 包管理器识别 prompts/ 约定并安装到 ~/.pigo/prompts — 2026-07-27

Design Decisions

Decision Source-dir lookup order: prompts/ > commands/ > root

Ambiguity: Which subdir does a prompt package ship its templates in?

Choice: Try prompts/ first (the pi convention), then the legacy commands/, then root-level *.md.

Rationale: pi packages use prompts/; pigo’s legacy convention was commands/. Supporting both (with prompts preferred) maximizes compatibility while aligning with pi.

Decision Install target is PromptsDir() (~/.pigo/prompts); CommandsDir() retained for back-compat

Ambiguity: Where do newly installed prompt templates land?

Choice: New installs go to $PIGO_HOME/prompts (new PromptsDir() in layout.go). CommandsDir() is kept because pre-#342 installs live in commands/ and their lockfile entries point there (uninstall must still find them).

Rationale: runtime.LoadUserCommandsDir loads both prompts/ and commands/ (per #336), so old installs keep working and new installs use the pi-aligned location.

Decision No migration of existing commands/ installs

Ambiguity: Should existing ~/.pigo/commands/*.md be moved to prompts/?

Choice: Leave them in place; they still load (back-compat) and their lockfile entries still point to commands/ for clean uninstall.

Rationale: Moving user files on upgrade is risky and unnecessary since both dirs are loaded. New installs use prompts/; old ones age out naturally.

Deviations

None — implementation follows US-012 as written. The prompts/ > commands/ > root lookup, install to PromptsDir, README.md skip at root, and the lockfile-path/uninstall tests match the acceptance criteria.

Tradeoffs

Tradeoff prompts/ wins outright when both prompts/ and commands/ exist

Alternatives: Merge templates from both subdirs.

Pros/cons: Picking prompts/ only is simpler and matches pi (one canonical subdir). Merging would install duplicate/legacy templates the package author likely didn’t intend.

Why it won: A package shipping both is rare; prompts/ is the canonical source. commands/ is a fallback for packages that haven’t migrated.

Tradeoff Keep CommandsDir() vs remove it

Alternatives: Remove CommandsDir() now that installs go to PromptsDir().

Pros/cons: Removing would orphan pre-#342 lockfile entries (uninstall couldn’t resolve commands/ paths). Keeping it costs one small function.

Why it won: Back-compat for existing installs and their lockfile entries; CommandsDir() is still referenced by the loader and uninstall paths.
