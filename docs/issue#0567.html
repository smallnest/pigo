Design Decisions

Decision Pluggable Runner with a default real runner

Ambiguity: The spec required session creation + prompt injection + read-only toolset, but not how (or whether) the webhook process should itself run the LLM.

Choice: Server.Runner is injectable; DefaultRunner resumes the just-created session, drives the loop with the read-only registry, and appends the reply. cmd/pigo --github-review wires the default; tests inject fakes.

Rationale: Keeps the webhook handler testable end-to-end without a live LLM, while the shipped mode performs the full review.

Decision Session persisted before the runner starts

Choice: createReviewSession writes the header + review prompt to disk first; the runner resumes from the store and appends its reply to the same session.

Rationale: The review input is durable even if the process dies mid-run, and the session can be reopened interactively with /resume — matching dsh's "root Session under the Web Workspace".

Decision Secret by env-var-name indirection

Choice: --github-webhook-secret-env names the environment variable carrying the secret (default PIGO_GITHUB_WEBHOOK_SECRET); the process refuses to start when it is unset.

Rationale: Mirrors dsh's credential-reference pattern — the secret never appears in config files, argv, or logs.

Deviations

Deviation Delivery-id dedupe instead of timestamp replay window

Spec: "并发/重放防护" without prescribing a mechanism.

Implemented: HMAC-SHA256 constant-time verification plus X-GitHub-Delivery id dedupe with a 24h TTL cache. GitHub does not send timestamps, so the delivery id is the natural replay token; a missing id is 202-ignored.

Deviation Default listener binds loopback (127.0.0.1:3081), plain HTTP

Why: Same as dsh's default; TLS terminates at the reverse proxy/tunnel documented in README. Binding loopback by default avoids accidentally exposing a plain-HTTP endpoint.

Tradeoffs

Tradeoff Read-only via tool-set allowlist, not a trust mode

Alternatives: a new "review trust level" threaded through the trust manager, or a filtered tool set.

Chosen: static allowlist (read/grep/find) in ReadOnlyTools.

Why: Structurally simple — the tools are never advertised, so the model cannot call them — and matches how the tool-policy boundary already works. A trust-level redesign would be over-engineering for one mode.

Open Questions

Question Should concurrent review runs be queued/capped?

Each accepted event currently spawns its own goroutine; a flood of ready-for-review events would run reviews in parallel (bounded only by the webhook source being GitHub + secret). A semaphore or work queue is a natural follow-up if a busy monorepo enables this mode.

Question Should the review result post back to GitHub?

Today the review lands in a local session (readable via /resume). Posting a summary comment back to the PR would need a GitHub token and write scope — deliberately out of scope for this issue.
