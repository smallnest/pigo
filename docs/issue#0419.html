Implementation Notes

Issue #419 — hooks: Dispatcher 接线骨架 + 单一 InstallHooks 装配 helper — 2026-07-30

Design Decisions

Decision Helper lives in cli/run, not runtime

Ambiguity: Where does hook→seam assembly belong?

Choice: internal/cli/run/hooks_install.go. runtime exposes only generic seams and never imports hooks; cli knows both Config.Hooks and the seams.

Rationale: Prevents a runtime→hooks→runtime import cycle and keeps runtime hook-agnostic, exactly as the issue and SPEC §2.2/§2.3 require.

Decision Combinator semantics per seam

Ambiguity: "generic combinators" — how should two seams merge?

Choice: BeforeToolCall: prev-first, block short-circuits (earlier gate authoritative). AfterToolCall: next's non-nil result wins (last-writer). ShouldStop: OR, prev short-circuits.

Rationale: Matches the trust→hook chain design (trust blocks authoritatively) and the last-writer-wins merge already used inside the Dispatcher (§5.4).

Deviations

Deviation InstallHooks wires no seam yet

Spec said: InstallHooks composes hook dispatch into RunConfig's seams.

Implemented instead: It builds (or nil-short-circuits) the Dispatcher and accepts *runtime.RunConfig for a stable signature, but attaches nothing. The chain* combinators are provided for #420–#424 to do the actual attaching.

Why: The issue explicitly scopes this to "骨架与空短路"; wiring concrete events here would be dead code until the event payloads (#420–#424) exist.

Tradeoffs

Tradeoff AfterToolCall combinator: sequential vs field-merge

Alternatives: (a) last-writer-wins on the whole result, (b) field-by-field merge of two AfterToolCallResults.

Chosen (a): Simpler and predictable; the executor already applies a single result field-by-field over the tool output.

Con: Two After seams both wanting to override different fields can't co-exist — acceptable now since only PostToolUse uses this seam; revisit if a second consumer appears.
