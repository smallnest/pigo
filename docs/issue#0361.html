Issue #361 — 迁移 provider 解析到 internal/provider — 2026-07-28

Design Decisions

Decision env 注入参数放在签名末位

Ambiguity: SPEC 只要求把 os.Getenv 注入为 env func(string) string，未规定参数位置。

Choice: ResolveProvider(model, baseURL, protocol, providerName string, env func(string) string)、ResolveBaseURL(spec, flag, env) 均把 env 放在最后一个参数。

Rationale: 与包内既有的 ResolveSpecialProvider(spec, model, baseURL, env) 约定一致，读者对同一包的注入风格有统一预期。

Decision PrintProviderHelp 放 internal/cli 而非 internal/provider

Ambiguity: Issue 要求 printProviderHelp 迁入 internal/cli，但它只消费 provider.ProviderSpecs()，理论上也可留在 provider 包。

Choice: 严格按 Issue 放入 internal/cli/providerhelp.go（package cli），依赖方向 cli → provider。

Rationale: help 文本是 CLI 表现层关注点；provider 包应只负责解析与驱动构造，不承担面向用户的 usage 渲染。方向 cli→provider 无环。

Deviations

Deviation 调用方仍传 os.Getenv 而非线程注入配置

Spec: "os.Getenv 注入为 env func(string) string"。

Implemented: 函数签名接受 env 注入，但 4 处生产调用点（run.go、btw_config.go、subagent_rpc.go、interactive.go）仍显式传 os.Getenv。

Why: 注入的目的是让测试控制环境；生产环境读真实进程 env 是正确行为。全链路传递一个 env 抽象超出本 Issue 范围，会污染多个调用签名。

Tradeoffs

Tradeoff --help 字节级一致的验证方式

Alternatives: (a) 保存迁移前二进制的 golden 输出做 diff；(b) 用注册表派生断言（TestPrintProviderHelp 校验每个 provider 名/env/protocol 都出现）。

Chosen: (b)，并人工核对 go run ./cmd/pigo --help 的 provider 块渲染不变。

Why: printProviderHelp 是逐字节整体搬移、逻辑零改动，golden 二进制在纯迁移下无额外价值；注册表派生断言能持续防止未来漂移，维护成本更低。

Tradeoff 测试随源码迁移到 internal/provider

Alternatives: (a) 测试留在 cmd/pigo 通过导出函数间接测；(b) 测试跟随源码迁入 provider 包同包直测。

Chosen: (b)——resolve_test.go 移入 internal/provider（8 个解析用例 + 2 个 base-url 用例），cmd/pigo 只保留 presetListing 的测试。

Why: 测试与被测代码同包，覆盖归属清晰，符合 Issue "相关测试随源码迁移"。
