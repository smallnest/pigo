Implementation Notes

Issue #542 — Responses 驱动 — 图片/reasoning — 2026-08-02

Design Decisions

Decision All streaming partials built through one buildPartial helper

Ambiguity: Adding a reasoning (thinking) block means every partial-emit site must now assemble thinking + text + tool calls in a consistent order. The spec says reasoning should render "like the chat driver" but doesn't prescribe how partials are constructed.

Choice: Introduced buildPartial(thinking, text, toolCalls) and routed all four emit sites (text delta, reasoning delta, tool-call done, and the no-completed fallback) through it.

Rationale: A single builder guarantees every cumulative snapshot orders content identically (thinking → text → tool calls) and can't drift as new event types are added; it also collapsed the three previously-duplicated inline partial constructions.

Decision minimal thinking level collapses to reasoning effort low

Ambiguity: pigo's ThinkingLevel enum has six values (off/minimal/low/medium/high/xhigh); the Responses API reasoning.effort field accepts only low/medium/high.

Choice: responsesReasoningEffort maps minimal→low, low→low, medium→medium, high/xhigh→high, and off/unset→"" (no reasoning param emitted).

Rationale: The chat driver forwards "minimal" verbatim, but the Responses API would reject it; low is the nearest supported floor. Emitting "" for off/unset keeps a non-reasoning request byte-identical to before this change.

Decision Reasoning enabled ⇒ request an auto summary

Ambiguity: The Responses API only returns a reasoning summary if one is requested; the spec says "reasoning 输出（若返回）与 chat 驱动一致地呈现" but doesn't say to request it.

Choice: When effort is non-empty, set Reasoning{Effort: effort, Summary: ReasoningSummaryAuto}.

Rationale: Without a summary request the model reasons but returns nothing to render; auto lets the API pick an appropriate summary granularity so a thinking block actually appears — satisfying the "presented like the chat driver" criterion.

Decision Images replayed only on non-assistant (user) messages

Ambiguity: The issue says "图片 content part 映射为 Responses-API input items" without naming which message roles carry images.

Choice: Image handling lives in the default (user) branch of appendInputItems via imageInputParts; the assistant and tool-result branches are unchanged.

Rationale: Images flow in on user turns in pigo, matching the chat driver's openAIUserContent which only builds multimodal parts for user content. Assistant/tool-result image replay is not a real path today.

Deviations

None — implementation followed the issue spec (image content parts mapped to input_image data URIs, thinking level mapped to reasoning.effort, reasoning output surfaced as a thinking block, and unit tests covering one image-input request and one reasoning-enabled request).

Tradeoffs

Tradeoff image_url data URI vs. file upload / hosted URL

Alternatives: Upload the image via the Files API and reference a file_id, or pass a hosted image_url.

Chosen: Inline data:<mime>;base64,<data> URI on an input_image part, with detail auto.

Why: pigo already holds image bytes as base64 in ImageContent; a data URI is a stateless single-request mapping that matches the chat driver's image_url approach and needs no extra upload round-trip or lifecycle management.

Tradeoff Reasoning parsed from response.completed, deltas only feed interim partials

Alternatives: Aggregate the terminal thinking block from the accumulated reasoning_summary_text.delta events.

Chosen: mapResponse re-reads reasoning from resp.Output (via item.AsReasoning()) for the terminal message; the delta events only drive interim StreamThinkingEvent partials.

Why: Same principle as #540/#541 — the completed envelope is authoritative, so the streamed terminal message stays byte-identical to a non-streamed one. Delta accumulation would risk drift between the two paths.

Open Questions

Question Streaming reasoning-delta path not covered by a dedicated test

The ResponseReasoningSummaryTextDeltaEvent case shares buildPartial with the (tested) text-delta path, and the reasoning output parse is tested via response.completed. But no test asserts a mid-stream StreamThinkingEvent fires from a reasoning delta frame. Acceptable for this milestone; confirm whether a streaming-thinking assertion is wanted.

Question Tool-result and assistant messages still flatten images to text

Only user-role messages emit image parts. A ToolResultMessage carrying an image is still serialized text-only via function_call_output (inherited from #541), and assistant messages replay text + tool calls only. Confirm no flow needs image round-tripping on those roles.

Question Image detail hard-coded to auto

Every input_image part uses detail auto; pigo's ImageContent carries no detail hint. If callers need high/low control (cost vs. fidelity), a mapping would need to be added upstream. Verify auto is an acceptable default.
