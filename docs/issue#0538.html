Design Decisions

Decision Standalone NormalizeProtocol in a new protocol.go

Ambiguity: US-001 says parsing should live "near ResolveProvider" but the wiring is a separate issue (#543).

Choice: Added a pure NormalizeProtocol(raw) (string, error) plus a ProtocolOpenAIResponses constant in a dedicated internal/provider/protocol.go, unused by production code for now.

Rationale: Keeps #538 independently shippable and testable; #543 consumes it without re-parsing surface syntax.

Decision openai and openai/chat both normalize to the existing ProtocolOpenAI

Ambiguity: Could introduce a fresh "chat" constant.

Choice: Reuse the existing ProtocolOpenAI = "openai" value so the Chat Completions path is byte-for-byte unchanged; only resp_api gets a new selector.

Rationale: Zero behavior change for current users (a stated PRD goal).

Tradeoffs

Tradeoff Normalize to string selectors, not a new enum type

Alternatives: Define a typed Protocol enum vs. keep string constants.

Chosen: Strings, matching the existing ProtocolOpenAI/ProtocolAnthropic convention.

Why: Consistent with registry code; avoids a churny type migration across resolve/registry for a value that is ultimately compared as a string.
