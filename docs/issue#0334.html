Design Decisions

Decision Description fallback uses the body after frontmatter removal; for no-frontmatter templates it uses the whole content

Ambiguity: Which text does the “first non-empty line” fallback scan — the raw file or the body after the frontmatter fence?

Choice: Scan body (the content after splitFrontmatter), which equals the whole file when there is no frontmatter.

Rationale: pi says “the first non-empty line is used” — that line is part of the prompt body, not the frontmatter. Scanning post-frontmatter body avoids ever picking up a YAML key as the description.

Decision ArgumentHint is stored verbatim with no format validation

Ambiguity: Should the <angle>/[square] convention be enforced?

Choice: Store the hint as-is; the <angle>/[square] convention is display-only (per the PRD’s Design Considerations: “仅展示约定，不做语义校验”).

Rationale: The hint is free-form text rendered in autocomplete; validating it would reject legitimate hints and add no behavior.

Deviations

None — implementation follows US-004 as written. argument-hint is parsed from frontmatter, SlashCommand.ArgumentHint carries it, description falls back to the first non-empty body line, both fields are optional, and the name override is preserved. The four test cases (only-description, only-hint, both, neither) match the acceptance criteria.

Tradeoffs

Tradeoff firstNonEmptyLine as a named helper vs inline

Alternatives: Inline the loop where the fallback is computed.

Pros/cons: A named helper is reusable and independently testable; inlining saves one function but mixes concerns.

Why it won: The fallback is a distinct, testable rule; a helper documents its contract (“first trimmed non-empty line”) in one place.

Tradeoff No markdown stripping in the description fallback

Alternatives: Strip a leading # from the first line so a heading isn’t used verbatim as the description.

Pros/cons: Stripping is friendlier for bodies that start with a heading; but pi’s spec just says “first non-empty line” with no mention of markdown stripping.

Why it won: Match the spec literally; avoid guessing pi’s markdown handling. Revisit if descriptions render poorly in autocomplete.
