Design Decisions

Decision "|"-split alternatives treated as exact names unless they contain regex metacharacters

Ambiguity: The SPEC lists matcher forms as empty/*, exact name, a|b multi-value, and regex — but write|edit is also valid Go regex, so which engine handles it is unclear.

Choice: Split on |; if every alternative is a "plain" token (no . * + ? ( ) [ ] { } ^ $ \), treat it as exact/multi-value matching and never fall through to regexp. Only patterns containing metacharacters (e.g. Edit.*) compile as regexp.

Rationale: Gives predictable exact-match semantics for the common write|edit case while still supporting real regexes, and avoids surprising partial-substring matches from an accidental regexp interpretation.

Decision continue:false mapped to a block

Ambiguity: The protocol lists a continue bool (from Claude Code) but the SPEC's HookDecision only models Block/Reason/AdditionalContext/UpdatedInput.

Choice: HookOutput.blocks() returns true for either decision:"block" or an explicit continue:false.

Rationale: Keeps v1 decision surface small (one "stop" concept) while honoring both spellings a hook author might use. A distinct "hard stop entire loop" semantic can be added later if needed.

Decision Non-positive per-hook timeout override is ignored

Ambiguity: SPEC says default 60s, overridable per hook, but does not say what a timeout:0 or negative means.

Choice: TimeoutSeconds() falls back to the 60s default unless the override is strictly positive.

Rationale: Prevents a misconfigured 0 from disabling the timeout guard entirely, which would let a hung hook freeze the agent — the exact failure mode the timeout exists to prevent.

Deviations

None — the package implements the SPEC's §3.1/§3.3/§5.2/§5.3/§6 contracts as written. No wiring into existing seams was done in this issue (deferred to #419+ per the SPEC phase plan).

Tradeoffs

Tradeoff Regexp compiled per Dispatch call rather than cached

Alternatives: (a) compile matcher regexps once at config-resolve time and cache; (b) compile lazily on each match.

Chosen: (b) — compile on each MatchHooks call.

Why: Keeps internal/hooks a pure leaf with no per-run state or lifecycle. Hook counts are tiny (typically 0–3 matchers per event) and only metacharacter matchers pay the cost, so the allocation is negligible against the shell-fork cost that follows. Caching can be introduced later behind the same API if profiling ever shows it matters.

Tradeoff Output cap keeps a truncated prefix instead of discarding on overflow

Alternatives: (a) drop all output once the 1MB cap is hit; (b) keep the first 1MB and count the dropped bytes.

Chosen: (b) via cappedBuffer.

Why: A hook that prints a small JSON decision followed by noise still has its decision parsed. The dropped-byte count drives a single truncation warning without unbounded memory growth.

Open Questions

Question Should invalid-hook / invalid-regexp warnings dedupe across repeated events?

Currently a malformed matcher warns on every event dispatch that touches it. For a hot event (PreToolUse fires per tool call) this could be noisy. Acceptable for v1? Or dedupe at resolve time once #418 adds config validation?

Question Windows shell support

The runner hardcodes sh -c (field-overridable). Per SPEC §11.1 v1 targets darwin/linux only. Confirm Windows is out of scope for this batch.
